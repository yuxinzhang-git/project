# 内容块类型与工具系统

## 要学习什么

Content Block 是组成消息内容的基本单元。XingClaw 定义了四种内容块，分别对应文本、思考过程、图片和工具调用。同时理解 Tool（工具定义）、Context（请求上下文）和相关辅助类型。

## 概念解释

### 四种 Content Block

#### TextContent — 普通文本

```python
@dataclass
class TextContent:
    type: Literal["text"] = "text"
    text: str = ""
    text_signature: Optional[str] = None
```

最基本的文本块，几乎所有消息的核心组成部分。

#### ThinkingContent — AI 的思考过程

```python
@dataclass
class ThinkingContent:
    type: Literal["thinking"] = "thinking"
    thinking: str = ""
    thinking_signature: Optional[str] = None
    redacted: bool = False
```

部分 AI provider（如 Claude）支持输出思考过程。`redacted` 字段表示内容是否被截断隐藏。

#### ImageContent — 图片数据

```python
@dataclass
class ImageContent:
    type: Literal["image"] = "image"
    data: str = ""
    mime_type: str = "image/png"
```

图片以 base64 编码传输，`mime_type` 标明格式。通常用于用户消息（发送图片）或工具结果（返回截图）。

#### ToolCall — 工具调用指令

```python
@dataclass
class ToolCall:
    type: Literal["toolCall"] = "toolCall"
    id: str = ""
    name: str = ""
    arguments: dict[str, Any] = field(default_factory=dict)
```

模型认为需要调工具时，会在回复中放一个 ToolCall。外部系统根据 `name` 找到对应函数，用 `arguments` 作为参数调用，结果通过 `ToolResultMessage` 返回。

### Content Block 的三种联合类型

```python
# AI 回复中可以包含：文本、思考过程、工具调用
AssistantBlock = Union[TextContent, ThinkingContent, ToolCall]

# 用户消息中可以包含：文本、图片
UserBlock = Union[TextContent, ImageContent]

# 工具结果中可以包含：文本、图片
ToolResultBlock = Union[TextContent, ImageContent]
```

每种消息的 `content` 字段限制为对应的联合类型，保证类型安全：

```python
assistant_msg = AssistantMessage(content=[
    TextContent(text="我来查一下天气"),
    ToolCall(id="call_001", name="get_weather", arguments={"city": "北京"}),
])

user_msg = UserMessage(content=[
    TextContent(text="这张图里有什么？"),
    ImageContent(data="base64...", mime_type="image/png"),
])
```

### Tool — 告诉 AI 有哪些工具可用

```python
@dataclass
class Tool:
    name: str
    description: str
    parameters: dict[str, Any]
```

`Tool` 是工具定义，告诉 AI：你有这些功能可以用，它们的参数是什么格式。AI 根据 `description` 决定是否调用这个工具。

```python
weather_tool = Tool(
    name="get_weather",
    description="查询某个城市的天气",
    parameters={
        "type": "object",
        "properties": {
            "city": {"type": "string", "description": "城市名"}
        },
        "required": ["city"],
    },
)
```

### Context — 一次请求的完整上下文

```python
@dataclass
class Context:
    messages: list[Message]
    system_prompt: Optional[str] = None
    tools: Optional[list[Tool]] = None
```

`Context` 把一次请求所需的所有信息打包在一起：消息历史 + 系统提示词 + 可用工具。Agent 拿到 `Context` 后就能发给 provider 获取回复。

```python
ctx = Context(
    system_prompt="你是一个助手",
    messages=[UserMessage(content="北京天气怎么样？")],
    tools=[weather_tool],
)
```

### 辅助类型

除了核心的数据模型，XingClaw 还定义了几个辅助类型来支持生产环境使用：

- **Usage** — token 使用统计。记录 input、output、cache_read、cache_write 各消耗了多少 token，以及总 token 数和对应成本。排查账单对不上的问题通常从这里入手。
- **Cost** — 成本统计。按 input、output、cache_read、cache_write 分别统计费用，total 为总和。单位通常是美元。
- **Model** — 模型配置。包括模型 id、名称、所属 API 和 provider、接口地址、是否支持推理（reasoning）、支持什么输入类型（text/image）、上下文窗口大小、最大输出 token 数等。
- **StreamOptions** — 流式调用的通用参数。可设置 temperature、max_tokens、API key、自定义请求头、超时时间、会话 ID 等。
- **SimpleStreamOptions** — StreamOptions 的扩展，额外支持 reasoning 等级（从 minimal 到 xhigh 逐步提高推理深度）。
- **StopReason** — 回答结束原因。取值包括：
  - “stop” — 正常结束
  - “length” — 超长截断
  - “toolUse” — 触发工具调用，等待工具结果
  - “error” — 生成过程出错
  - “aborted” — 被外部中断
- **ThinkingLevel** — 简化接口的推理等级，从 minimal 到 xhigh 逐步加强推理深度。

### 设计原则

- **对外暴露稳定模型**：所有 provider 的私有字段都归一为这些数据类，调用方不依赖某个 AI 厂商的特殊格式
- **Content Block 拆分**：不同类型的内容用独立的数据类表示，方便扩展（比如新增一个 AudioContent 只需加一个类，不改其他代码）
- **Union 类型限制范围**：不同消息类型只能包含对应 Content Block，防止误用（比如 ToolCall 不会出现在用户消息里）


## 总结：Message、Content Block与 Context 的关系

整个数据模型围绕一个核心流程设计：

`
用户输入 → UserMessage(UserBlock[])
    ↓
AI 处理 → AssistantMessage(AssistantBlock[])
    ↓ (可选) 如果 AI 决定调工具
AssistantMessage(ToolCall) → 执行工具 → ToolResultMessage(ToolResultBlock[])
    ↓
继续对话 → 新的 UserMessage
`

**关键关系：**

- **Content Block** 是消息的基本组成单元。一共有四种：TextContent、ThinkingContent、ImageContent、ToolCall
- **Union 类型**（AssistantBlock、UserBlock、ToolResultBlock）限制每种消息能包含哪些 Content Block，保证类型安全
- **Message** 是消息的基本单位。三种消息（UserMessage、AssistantMessage、ToolResultMessage）组成完整的对话历史
- **Context** 把消息历史 + 系统提示词 + 可用工具列表打包在一起，作为一次请求的完整输入

**数据走向：**

1. 用户发送消息 → 创建 UserMessage（content 可以是纯文本字符串，也可以是 list[UserBlock] 包含文本和图片）
2. AI 收到请求后处理 → 创建 AssistantMessage（content 是 list[AssistantBlock]，可包含文本、思考过程、工具调用）
3. 如果 AI 决定调工具 → AssistantMessage.content 中包含一个或多个 ToolCall（每个 ToolCall 有唯一 id、工具 name 和参数 arguments）
4. 系统执行工具 → 创建 ToolResultMessage（tool_call_id 与上一步的 ToolCall.id 配对，告诉 AI 这个结果对应哪个调用）
5. 把 ToolResultMessage 加回消息历史 → AI 拿到结果后继续生成回复（可能继续调工具或最终回复用户）

**用到的辅助类型：（常为AssistantMessage的配置参数）**

- Usage / Cost：记录每次请求的 token 消耗和费用，用于监控和计费
- Model：定义模型配置，决定请求发给哪个 API、用什么协议
- StreamOptions：控制流式调用的参数（temperature、max_tokens、超时等）
- StopReason：告诉调用方为什么停止生成，方便处理异常情况
